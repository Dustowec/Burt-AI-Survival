TZ-9-REV: encounter reveal via osmotret; ambush only in thicket
==================================================================
Финальные решения по вопросам:
1. Инициатива при атаке раскрытого случайного энкаунтера:
   - всегда Бурт;
   - никакого free strike;
   - стандартный порядок боя: Бурт -> враги.

2. Действие attack_{enemy_id}:
   - только начинает бой;
   - первый фактический удар происходит следующим боевым действием;
   - сам момент атаки из раскрытого энкаунтера не разрешает раунд.

3. Случайный энкаунтер как отдельный класс rnd_event:
   - выносится в отдельное ТЗ;
   - в этой задаче не реализовывать;
   - инициатива 1d6 для случайных встреч в этой задаче не делать.

4. Показ монстра:
   - строка "You see:" показывается один раз, в результате osmotret;
   - постоянного инжекта в сенсорный отчёт не делать.

==================================================================
ЦЕЛЬ
==================================================================

Изменить поведение случайных встреч в не-ambush локациях:

1. При входе в forest / field / steppe / swamp / dungeon:
   - бросок спавна остаётся;
   - если монстры заспавнились, бой НЕ начинается;
   - создаётся hidden["pending_encounter"].

2. В локации с pending_encounter действие osmotret:
   - раскрывает встречу;
   - добавляет в события "You see: ...";
   - устанавливает hidden["encounter_revealed"] = True.

3. Пока encounter_revealed=True:
   - меню состоит только из:
     - attack_{enemy_id} для каждого врага;
     - go_away_to_{direction} для каждого доступного выхода.

4. attack_{enemy_id}:
   - начинает бой с initiative="burt";
   - free_strike_done=True;
   - бой начинается без "Ambush!";
   - фактическая атака Бурта происходит уже следующим боевым действием.

5. go_away_to_{direction}:
   - очищает pending_encounter и encounter_revealed;
   - выполняет обычный переход go_{direction};
   - побег/уход теряет монстра.

6. Любой валидный go_* из локации с нераскрытым pending_encounter:
   - очищает pending_encounter;
   - монстр теряется при попытке ухода.

7. Thicket:
   - ambush остаётся как сейчас;
   - бой начинается сразу;
   - initiative="enemy";
   - pending_encounter не создаётся.

FIX 4. burt/loop.py — вспомогательные функции

   последующего самовосстановления через _clear_pending_encounter.

3. _preview_pending_enemies(enemy_keys) -> list

   Использует:
     preview = combat.start_combat(enemy_keys, "burt")

   Возвращает список врагов с полями:
   - id
   - key
   - display name через ENEMIES

   Если combat.start_combat бросает исключение:
   - встреча считается битой;
   - вызывающий код должен очистить состояние.

==================================================================
FIX 6. burt/loop.py — очистка встречи при смене ноды
==================================================================

Нужно гарантировать, что старая встреча не переносится в другую ноду.

Правила:

1. В обычном обработчике go_{direction}:
   - после проверки, что выход существует;
   - до броска движения;
   - вызвать _clear_pending_encounter(hidden).

2. Если направление невалидно или выхода нет:
   - ошибку вернуть;
   - pending не очищать.

3. В go_back:
   - после успешного возврата в source-ноду
   - очистить старый pending.

4. В go_forward:
   - после перехода в target-ноду
   - очистить старый pending до вызова _maybe_start_combat_on_enter.

5. Если после перехода новая локация имеет собственный спавн:
   - _maybe_start_combat_on_enter может создать новый pending.

Итог:
- любая валидная попытка ухода из локации теряет старый нераскрытый энкаунтер;
- невалидная попытка ухода энкаунтер не теряет;
- после успешного входа в новую ноду может появиться новый энкаунтер.

FIX 9. burt/loop.py — execute_action, encounter guard
==================================================================

Добавить обработку раскрытой встречи в execute_action.

Условия срабатывания:
- current_mode != "combat";
- hidden["combat"] is None;
- нет активной микролокации;
- hidden["encounter_revealed"] == True;
- pending_encounter валиден.

Если pending невалиден:
- _clear_pending_encounter(hidden)
- продолжить обычную обработку действия.

Если pending валиден:

--------------------------------------------------
9.1. Действие attack_{enemy_id}
--------------------------------------------------

Если action.key начинается с "attack_":

1. Получить список разрешённых врагов через _preview_pending_enemies.
2. Проверить, что выбранный target_id существует в этом списке.
3. Если target_id неверный:
   - вернуть error_result;
   - бой не начинать;
   - шаг не увеличивать;
   - pending не очищать.
4. Если target_id верный:
   - _clear_pending_encounter(hidden)
   - hidden["step"] += 1
   - combat_report = _start_combat(enemy_keys, "burt", hidden, visible)
   - вернуть ActionResult(events=[combat_report])

Важно:
- это действие только начинает бой;
- не вызывать combat.resolve_round;
- не наносит урон;
- не создаёт события "You hit" / "You missed";
- не должно быть "Ambush!";
- после этого боя первый фактический удар Бурта будет следующим
  боевым действием.

--------------------------------------------------
9.2. Действие go_away_to_{direction}
--------------------------------------------------

Если action.key начинается с "go_away_to_":

1. Извлечь направление.
2. Проверить:
   - направление входит в DIRECTIONS;
   - выход реально существует в текущей локации.
3. Если направление невалидно или выхода нет:
   - вернуть error_result;
   - pending не очищать.
4. Если направление валидно:
   - _clear_pending_encounter(hidden)
   - выполнить обычный go_{direction} ровно один раз.

Требования к делегированию:
- нельзя рекурсивно вызывать execute_action, если это приводит к
  повторным побочным эффектам;
- разрешено вынести обработку обычного движения в отдельную
  внутреннюю функцию и вызвать её;
- побочные эффекты должны быть такими же, как у обычного go_{direction}:
  - один шаг при успешном движении или при движении с провалом;
  - одна запись last_action;
  - одна обработка движения;
  - одна возможная микролокация;
  - один возможный вход в новую ноду.

--------------------------------------------------
9.3. Любое другое действие
--------------------------------------------------

Если encounter_revealed=True, pending валиден,
а действие не является attack_* или go_away_to_*:

- вернуть error_result;
- состояние встречи не менять;
- шаг не увеличивать.

==================================================================
FIX 11. Поведение шага
==================================================================

Правила:

1. Вход в локацию:
   - шаг увеличивает обычное движение, как сейчас.

2. osmotret:
   - увеличивает шаг, как сейчас.

3. Инициация боя через attack_{enemy_id}:
   - увеличивает шаг ровно на 1.

4. Последующие боевые действия:
   - не увеличивают шаг;
   - счётчик шага заморожен на время боя.

Это соответствует спеке: бой может состоять из нескольких раундов,
но дневной счётчик за бой не должен прибавляться за каждый раунд.

==================================================================
ПОВЕДЕНИЕ БОЯ ПОСЛЕ ИНИЦИАЦИИ
==================================================================

После attack_{enemy_id}:

1. hidden["current_mode"] = "combat"
2. hidden["combat"]["initiative"] = "burt"
3. hidden["combat"]["free_strike_done"] = True
4. pending_encounter отсутствует
5. encounter_revealed отсутствует

Первый фактический боевой ход:
- игрок выбирает обычное боевое действие;
- если выбран атаковать цель:
   - сначала Бурт атакует цель;
   - затем живые враги действуют по порядку;
- "Ambush!" не появляется.
